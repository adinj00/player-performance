# Unit 42: Media UI Foundation

## Goal

Build the first complete media frontend experience using the Unit 41 media APIs and Unit 40 storage-backed content access. Add a team-scope-aware media library, streamed upload and external-reference dialogs, media detail and lifecycle actions, explicit match/report/player attachment workflows, and real media sections on existing match and player detail screens. Add only the two minimal backend support queries required for runtime upload capabilities and authoritative link candidates, without introducing media processing, thumbnails, playlists, training/import attachments, public file URLs, or a global audit UI.

### Minimal media-capabilities endpoint

Add:

```txt
GET /api/media/capabilities
```

Purpose:

- expose the effective runtime media upload limit;
- expose the stable uploaded file/category pairs implemented by Unit 41;
- prevent the frontend from hardcoding environment-specific size configuration;
- keep file-picker accept hints aligned with backend behavior.

Authorization:

- authenticated active user required;
- no team parameter;
- no mutation permission required;
- response contains no secrets, storage provider, root path, storage key, or infrastructure details.

Return at minimum:

```txt
maxUploadSizeBytes
uploadedFileTypes:
  category
  extensions
  contentTypes
externalReferenceCategories
```

Example conceptual item:

```txt
category = VIDEO
extensions = [".mp4", ".webm", ".mov"]
contentTypes = ["video/mp4", "video/webm", "video/quicktime"]
```

Rules:

- values come from the same Unit 41 configuration/allowlist used by upload validation;
- do not duplicate a second backend capability matrix;
- deterministic ordering;
- cache-safe authenticated read;
- no database access is required;
- no migration is required.

Add backend tests for:

- authenticated access;
- unauthenticated rejection;
- effective configured maximum;
- deterministic supported pairs;
- no storage-provider/path leakage.

### Minimal link-candidate endpoint

Add:

```txt
GET /api/media/{mediaId}/link-candidates
```

Supported query parameters:

```txt
targetType
search
page
pageSize
```

Stable target values:

```txt
MATCH
MATCH_REPORT
PLAYER
```

Purpose:

- provide authoritative selectable targets for the media detail attachment UI;
- avoid reproducing match-report workflow locks in the browser;
- avoid using current player assignments when Unit 41 player linking accepts any historical/current/future assignment to the media team;
- exclude targets already actively linked.

Authorization:

- authenticated active user;
- media must be active;
- caller must have Unit 41 link mutation capability for the media team:
  - `ADMIN`; or
  - in-scope `DATA_OPERATOR`;
- inaccessible media follows existing safe behavior;
- read-only roles receive `403`.

Candidate behavior:

#### `MATCH`

Return matches that:

- belong to the media team;
- are not archived;
- are not cancelled;
- are not already actively linked;
- are currently linkable under the Unit 41 report-lock rule.

#### `MATCH_REPORT`

Return reports that:

- belong to a match for the media team;
- are not archived;
- are not already actively linked;
- currently permit media editing under Unit 32/41 workflow rules.

#### `PLAYER`

Return players that:

- are not archived;
- have at least one historical, current, or future assignment to the media team;
- are not already actively linked.

Candidate read model contains at minimum:

```txt
id
targetType
primaryLabel
secondaryLabel
status
```

Examples:

- match: opponent/date/competition;
- report: match identity/report status;
- player: display name and relevant assignment/team context.

Rules:

- backend pagination;
- bounded normalized search;
- deterministic ordering;
- candidate results are UX support only;
- existing Unit 41 link endpoints remain authoritative;
- state may change between candidate query and mutation;
- no target mutation occurs through this endpoint;
- no migration is required.

Add focused tests for:

- each target type;
- team equality;
- workflow locks;
- existing active-link exclusion;
- historical player assignment inclusion;
- archived target exclusion;
- role/team-scope authorization;
- pagination/search;
- stale-state safety.

### URL-driven media filters

Use `nuqs`.

Support at minimum:

```txt
search
teamId
sourceType
category
includeArchived
linkedTargetType
linkedTargetId
page
mediaId
```

Internal source values:

```txt
UPLOADED_FILE
EXTERNAL_REFERENCE
```

Internal category values:

```txt
VIDEO
IMAGE
DOCUMENT
OTHER
```

Rules:

- search is debounced using the established frontend pattern;
- discrete filters update without debounce;
- changing any filter resets page to 1;
- invalid URL values normalize safely;
- server-side Unit 41 filtering/pagination remains authoritative;
- do not load all media and filter client-side;
- archived visibility is separate from source/category;
- `includeArchived` is shown only to `ADMIN`;
- target type and target ID are applied together;
- changing target type clears an incompatible target ID;
- selected-team users are not offered out-of-scope teams;
- provide `Očisti filtere` when non-default filters are active.

Do not add a season filter because Unit 41 does not expose a season media filter.

Do not infer season by loading and joining every linked match client-side.

A future season filter requires a backend contract change.

### Upload progress and cancellation

Use browser-native `XMLHttpRequest` for this endpoint because the Fetch API does not provide standard upload-progress events.

Do not add Axios or another upload package.

The media upload client must:

- use the existing API base URL convention;
- include credentials/cookies;
- include the existing CSRF header/token required by mutation endpoints;
- parse success DTOs;
- parse ProblemDetails responses safely;
- expose upload progress when total size is known;
- expose an indeterminate state when total progress cannot be calculated;
- prevent duplicate submissions;
- support user-requested abort;
- preserve form metadata after ordinary validation/server errors.

Use shadcn `Progress`.

Suggested states:

```txt
Priprema uploada
Učitavanje
Završavanje
Uspješno učitano
Upload nije uspio
```

Cancellation caveat:

- aborting the browser request may race with server completion;
- after abort, invalidate/refetch the media list;
- show neutral copy such as:
  `Zahtjev je prekinut. Provjerite medijateku jer je server možda već završio obradu.`
- do not claim guaranteed rollback from the browser.

When closing a dialog during active upload:

- require explicit confirmation;
- abort only after confirmation;
- refetch afterward.
